# 04 — Determinism, CI feasibility, and git storage

Questions: (1) what breaks font-rasterization determinism across machines and whether a pinned font + pure-Rust rasterizer or a container achieves byte-identical output; (2) whether PNG encoding is byte-deterministic and what comparison mode established snapshot tools use; (3) what this repo's CI lanes (velnor self-hosted + ubuntu-26.04 GitHub) imply for a PNG job, including GPU/display needs; (4) what actually happens when macOS devs bless and Linux CI verifies, and what real projects do; (5) plain git vs git-LFS economics for ~100–300 small PNGs rewritten on design changes; (6) what GitHub's PR web UI shows for changed PNGs.
Informs: jackin-termrock-parity
Method: web + codebase read
Vetted: 2026-08-16

## Findings

### 1. Font-rendering determinism

- System text stacks are inherently machine-variable: FreeType changed its default TrueType interpreter to v40 in FreeType 2.7 ("FreeType 2.7 ships the new v40 TrueType instructions interpreter version enabled by default"), and v40 "simply ignores *all* horizontal hinting instructions" — so the same font renders differently under v35 vs v38 vs v40, i.e. across FreeType versions — https://freetype.org/freetype2/docs/hinting/subpixel-hinting.html (confidence: HIGH)
- matplotlib's image-comparison suite was broken by exactly this: FreeType version drift changes glyph pixels enough to fail baselines (issue "Varying results depending on freetype version", https://github.com/matplotlib/matplotlib/issues/8796), and matplotlib's fix was to build a pinned local FreeType for testing (PR "Use a specific version of Freetype for testing", https://github.com/matplotlib/matplotlib/pull/5306; `MPLLOCALFREETYPE` per https://matplotlib.org/2.1.0/devel/testing.html) (confidence: MED — repo issue/PR located and titles read; page bodies summarized via search, not read in full)
- Playwright states the general form of the problem: "Browser rendering can vary based on the host OS, version, settings, hardware, power source (battery vs. power adapter), headless mode, and other factors" and "Screenshots differ between browsers and platforms due to different rendering, fonts and more, so you will need different snapshots for them" — https://playwright.dev/docs/test-snapshots (confidence: HIGH)
- macOS uses CoreText, not FreeType, for its native text stack (e.g. ghostty: "a true Metal renderer with CoreText for font discovery" — https://github.com/ghostty-org/ghostty), so any pipeline that touches the OS text stack cannot match Linux FreeType output byte-for-byte (confidence: HIGH for the CoreText fact; the cross-stack mismatch itself is corroborated by the Playwright per-platform snapshot policy above)
- fontconfig is Linux font *selection/configuration* ("a library for configuring and customizing font access", https://www.freedesktop.org/wiki/Software/fontconfig/); it only enters the picture when fonts are discovered from the system. A pipeline that loads one pinned font file bypasses fontconfig entirely (confidence: MED — fontconfig description not re-fetched this session; bypass claim is inference from architecture)
- Pure-Rust rasterizer options, per their own repos:
  - fontdue: "a simple, `no_std` … pure Rust, TrueType (.ttf/.ttc) & OpenType (.otf) font rasterizer and layout tool"; README does not mention hinting, subpixel rendering, or determinism; explicitly defers shaping and points to cosmic-text — https://github.com/mooman219/fontdue (confidence: HIGH)
  - swash: "a pure Rust, cross-platform crate" with scaling, "asymmetric vertical hinting (TrueType and Postscript)", full variation support — https://github.com/dfrg/swash (confidence: HIGH)
  - cosmic-text: "Pure Rust multi-line text handling"; shaping by HarfRust, rendering by swash, font loading via fontdb; Linux/macOS/Windows "supported with the full feature set" — https://github.com/pop-os/cosmic-text (confidence: HIGH)
  - ab_glyph: "Fast API for loading, scaling, positioning and rasterizing OpenType font glyphs"; ab_glyph_rasterizer is "zero dependency coverage rasterization for lines, quadratic & cubic beziers" — https://github.com/alexheretic/ab-glyph (confidence: HIGH)
- None of the four documents a byte-determinism or cross-platform bit-identity guarantee. With a pinned font file + pinned crate versions the pipeline has no OS text-stack input (no FreeType, no CoreText, no fontconfig), so the remaining variance surface is the crates' own float math across architectures — plausible-identical but undocumented and unverified (confidence: MED — inference from primary-source dependency lists; the residual float question is an open unknown below)
- Containerization is the ecosystem's proven alternative when the stack is *not* pure: matplotlib pins a FreeType build; Playwright ships an official Docker image bundling browsers and "browser system dependencies" (https://playwright.dev/docs/docker) and its docs require running "in the same environment where the baseline screenshots were generated" (https://playwright.dev/docs/test-snapshots) (confidence: HIGH)

### 2. PNG encoding determinism

- The Rust `png` crate (image-rs/image-png) is a "robust and performant PNG decoder/encoder in pure Rust"; its fast encoding mode is "powered by fdeflate" — https://github.com/image-rs/image-png (confidence: HIGH)
- The `png` `Encoder` writes text ancillary chunks (`tEXt`/`zTXt`/`iTXt`) only via explicit `add_text_chunk`/`add_ztxt_chunk`/`add_itxt_chunk` calls; no `tIME` or other timestamped chunk is emitted by default; default filter is `Filter::Adaptive` — https://docs.rs/png/latest/png/struct.Encoder.html (confidence: HIGH). So same crate version + same options + same RGBA ⇒ same bytes is plausible (no time/random inputs), but no determinism guarantee is documented (confidence: MED — inference)
- Encoded bytes are NOT stable across crate versions: the changelog shows repeated compression-pipeline swaps — 0.16.5 "switched to miniz_oxide", 0.17.6 "switched to using the flate2 crate for encoding", 0.17.8 "make the 'fast' compression preset use fdeflate", 0.17.0 added adaptive filtering, 0.18.1 added `Filter::MinEntropy` — https://github.com/image-rs/image-png/blob/master/CHANGES.md (confidence: HIGH). Any dependency bump can rewrite every baseline byte even when pixels are unchanged (confidence: HIGH — direct consequence)
- The DEFLATE layer offers no cross-implementation byte guarantee; the zlib FAQ addresses interoperability ("can I exchange compressed data between [architectures]? Yes and yes") but never promises identical compressed output across versions or settings — https://zlib.net/zlib_faq.html (confidence: HIGH for the absence; the variability itself follows from the spec constraining only the decoded result)
- What established tools compare:
  - Playwright compares decoded pixels via pixelmatch with `maxDiffPixels`/threshold options — https://playwright.dev/docs/test-snapshots (confidence: HIGH)
  - pixelmatch (v7+) does per-pixel perceptual comparison in OKLab ("OKLab HyAB metric used to compare colors"), threshold 0–1 default 0.1, with anti-aliasing detection (`includeAA` false by default) — https://github.com/mapbox/pixelmatch (confidence: HIGH)
  - odiff compares pixels with "the YIQ NTSC transmission algorithm", threshold 0–1, optional anti-aliasing ignore — https://github.com/dmtrKovalenko/odiff (confidence: HIGH)
  - jest-image-snapshot: pixelmatch (default) or experimental SSIM; `failureThresholdType` `pixel` or `percent` — https://github.com/americanexpress/jest-image-snapshot (confidence: HIGH)
  - pytest-mpl: decoded-image RMS tolerance ("if the RMS of the residual is larger than a user-specified tolerance, the test will fail") plus an alternative hash mode and hybrid mode — https://pytest-mpl.readthedocs.io/en/latest/ (confidence: HIGH)
  - insta binary snapshots are the byte-compare outlier: "Binary snapshots store their content in a separate file next to the metadata file… They are simply compared byte for byte", and are marked experimental — https://insta.rs/docs/snapshot-types/ (confidence: HIGH)
- Net finding: every image-native snapshot tool surveyed compares decoded pixels (usually with a tolerance), not encoded bytes; byte-compare appears only in insta's generic binary snapshots, which are format-agnostic. Decode-then-compare makes the gate immune to encoder-version byte drift while still catching any pixel change; exact-zero-tolerance pixel compare retains bit-exactness of the *image* without freezing the *encoder* (confidence: HIGH — synthesis of the primary sources above)

### 3. CI runners in this repo

- PR CI is fully delegated: `.github/workflows/ci.yml` is generated ("Generated by velnor-actions-generator. DO NOT EDIT.", /Users/donbeave/Projects/tailrocks/termrock/.github/workflows/ci.yml:1) and calls `tailrocks/velnor-actions/.github/workflows/ci-code.yml` pinned at SHA `d6ebc786…` # 2026.8.25 (ci.yml:128). A new PNG job therefore lands in the velnor-actions reusable workflow (or its generator), not in this repo's workflow file (confidence: HIGH — file read)
- The PR lane is Velnor self-hosted by default: `lane: … || 'velnor'` for non-dispatch events (ci.yml:108,130); only `workflow_dispatch` can select `github`/`both` (ci.yml:24–32). The only GitHub-hosted job in ci.yml is the `ci-required` aggregator on `ubuntu-26.04` (ci.yml:172), which runs no build steps (confidence: HIGH)
- docs.yml shows both lanes concretely: Velnor = `["self-hosted","velnor-target-mvp"]`, GitHub = `ubuntu-26.04` (/Users/donbeave/Projects/tailrocks/termrock/.github/workflows/docs.yml:39), with mise, mold, sccache toolchains (docs.yml:41–58). Bless-required byte equality across a self-hosted fleet requires the render toolchain to be pinned independently of runner drift; the repo's existing mechanism for that is lockfiles + pinned action SHAs, not a container (no container: or docker usage appears in any workflow) (confidence: HIGH — files read)
- Precedent inside the repo: the docs pipeline already enforces render byte-determinism by rendering the lookbook twice and `diff -r`-ing the outputs (docs.yml:115–118). That gate covers the current renderer, which emits SVGs, not PNGs (`write_svgs`, /Users/donbeave/Projects/tailrocks/termrock/crates/termrock-lookbook/src/main.rs:159,305); no font/PNG/image crate exists in any Cargo.toml today (grep across `**/Cargo.toml` for fontdue|swash|cosmic-text|ab_glyph|freetype|png|image: zero hits) (confidence: HIGH)
- GPU/display need depends entirely on the capture strategy: rasterizing the Ratatui `Buffer` directly with a pure-Rust glyph rasterizer is headless CPU work needing no GPU, no GL, no X server (confidence: HIGH — inference from the crates' dependency claims in Q1). Screenshotting a real terminal emulator would need one: ghostty's "renderer uses OpenGL on Linux and Metal on macOS" (https://github.com/ghostty-org/ghostty), so a Linux CI capture would need a display server plus GL — Mesa's llvmpipe is "a software rasterizer that uses LLVM to do runtime code generation" running GL entirely on CPU (https://docs.mesa3d.org/drivers/llvmpipe.html) (confidence: HIGH for both quotes). Whether the ubuntu-26.04 hosted image preships Xvfb/Mesa was not confirmed from the runner-images README (confidence: LOW — see open unknowns). Metal has no software equivalent on a Linux runner, so an emulator-capture approach can never produce macOS-native pixels in this CI (confidence: MED — inference)
- macOS-vs-Linux consistency therefore has exactly two working shapes given this CI: (a) a capture pipeline with zero OS-stack inputs (pure-Rust rasterizer + pinned font + pinned crates), which is OS-independent by construction, or (b) one canonical Linux environment (container or pinned toolchain) that both CI and bless runs use — the matplotlib/Playwright pattern from Q1/Q4 (confidence: MED — synthesis)

### 4. Cross-platform bless reality

- When the render touches any OS text stack, macOS-blessed PNGs will not match Linux CI: Playwright institutionalizes this by writing platform-suffixed snapshot files (e.g. `example-test-1-chromium-darwin.png`) — separate baselines per OS — and instructs "for consistent screenshots, run tests in the same environment where the baseline screenshots were generated" — https://playwright.dev/docs/test-snapshots (confidence: HIGH)
- swift-snapshot-testing shows the failure mode persists even within one OS: snapshots generated on Apple Silicon vs Intel machines differ at the pixel level with identical simulator/OS/Xcode (issue https://github.com/pointfreeco/swift-snapshot-testing/issues/424), and the project's response was tolerance, not determinism: `perceptualPrecision` ("how perceptually similar a pixel must be") added in PR https://github.com/pointfreeco/swift-snapshot-testing/pull/628 (confidence: MED — issue/PR located and summarized via search, bodies not fully read)
- Observed team strategies, by strength of source:
  - Pin the rasterization stack (matplotlib: build a specific FreeType for tests — https://github.com/matplotlib/matplotlib/pull/5306) (confidence: MED)
  - Bless inside the CI-identical container (Playwright's official image, https://playwright.dev/docs/docker, used as the bless environment via `--update-snapshots` inside `mcr.microsoft.com/playwright:…`) — the image is primary, the bless-in-docker workflow is community practice (e.g. https://egghead.io/lessons/github-generate-playwright-snapshots-on-your-ci-server) (confidence: MED — official image HIGH, workflow pattern from secondary sources)
  - CI-as-blesser: CI regenerates snapshots and commits/uploads them so no dev machine ever produces baselines (community pattern, e.g. https://medium.com/@qa.gary.parker/%EF%B8%8F-automatic-snapshot-creation-in-ci-for-playwright-261bb1c9cdad) (confidence: LOW — blog lead only)
  - Per-platform baseline sets (Playwright's default file naming, above) (confidence: HIGH)
  - Tolerance instead of identity (swift-snapshot-testing `perceptualPrecision`; pytest-mpl RMS; jest-image-snapshot `failureThreshold`) (confidence: HIGH for the tools' mechanisms)
- jest-image-snapshot's README, despite the tool's popularity for exactly this problem, contains no cross-platform/Docker guidance at all — the ecosystem handles the gap in blog posts and thresholds, not in the tool — https://github.com/americanexpress/jest-image-snapshot (confidence: HIGH for the absence)
- For termrock's settled bless-required gate (CI regenerates; mismatch fails unless the PR carries regenerated PNGs), the macOS-dev/Linux-CI split is only closed by one of: OS-independent renderer, container bless, or CI-produced commits — Playwright-style per-platform baselines are incompatible with a single-source-of-truth gate (confidence: MED — synthesis)

### 5. Git storage economics

- Set size arithmetic (method: given N ≈ 20 families × 5–15 states = 100–300 PNGs at 5–50 KB): full baseline set ≈ 0.5–15 MB, central estimate ~2–6 MB. Terminal-grid phosphor renders are flat-color images that sit at the small end of PNG sizes (confidence: HIGH for the arithmetic; the per-file size range is an estimate pending a real render)
- History growth: PNGs are already deflate-compressed, so git's pack-time delta/zlib passes recover little; each design-change rewrite adds roughly one full set of new blob bytes to permanent history. Ten full-set rewrites ≈ 5–150 MB (worst case) of pack growth. Current repo pack is 118.17 MiB (method: `git count-objects -vH`), so even the worst case roughly doubles, not explodes, the repo (confidence: MED — arithmetic HIGH; "compressed data doesn't delta" is standard git behavior asserted without a fetched primary source)
- Plain-git platform limits are far away: warning at >50 MiB/file, hard block at 100 MiB/file, repos "ideally … under 1 GB, and less than 5 GB is strongly recommended" — https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github (confidence: HIGH)
- Git LFS quotas: Free/Pro/Free-org get 10 GiB storage + 10 GiB bandwidth included; Team and Enterprise Cloud get 250 GiB + 250 GiB; overage is metered ("Bandwidth is billed for each GiB of data downloaded. Storage is billed by calculating an hourly usage rate"), exact rates deferred to the pricing calculator — https://docs.github.com/en/billing/managing-billing-for-git-large-file-storage/about-billing-for-git-large-file-storage and https://docs.github.com/en/enterprise-cloud@latest/billing/concepts/product-billing/git-lfs (confidence: HIGH for quotas). Reported metered rates: $0.07/GiB-month storage, $0.0875/GiB bandwidth (GitHub changelog https://github.blog/changelog/2024-06-03-new-enterprise-accounts-have-metered-billing-for-git-lfs/ and https://github.com/orgs/community/discussions/61362) (confidence: MED — numbers not on the docs billing page itself)
- LFS per-file caps: 2 GB (Free/Pro), 4 GB (Team), 5 GB (Enterprise Cloud) — https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage (confidence: HIGH) — irrelevant at these file sizes
- The decisive LFS fact for this feature: GitHub's docs state "GitHub does not render some Git LFS objects in pull requests. Only the pointer file is shown" — https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage — confirmed for image diffs specifically by https://github.com/orgs/community/discussions/15267 ("Image diffs do not show when images are on git-lfs"). LFS is therefore incompatible with the settled requirement that the reviewer sees a before/after image diff in the PR (confidence: HIGH)
- Clone impact: every historical PNG blob ships with a full clone; `git clone --filter=blob:none` (partial clone, https://git-scm.com/docs/partial-clone) defers blob download — at the 5–150 MB scale above, clone impact is minor either way (confidence: MED — partial-clone doc not fetched this session)

### 6. GitHub PR review of image diffs

- For plain-git (non-LFS) PNGs, GitHub renders rich image diffs in PRs with three modes: "2-up is the default mode; it gives you a quick glimpse of both images"; swipe "lets you view portions of your image side by side"; "Onion Skin really comes in handy when elements move around by small, hard to notice amounts". Supported formats: "PNG, JPG, GIF, PSD, and SVG" — https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files (confidence: HIGH)
- That page documents no size limit for image rendering/diffing (confidence: HIGH for the absence on the page; actual limit unknown — see open unknowns). General per-file limits from Q5 (50 MiB warn / 100 MiB block) bound the worst case; few-KB terminal PNGs are far below any plausible rendering cutoff (confidence: MED)
- LFS-tracked images do not get this treatment: pointer file only (sources in Q5) (confidence: HIGH)

## Dead ends and contradictions

- pixelmatch is widely described (including by odiff's README) as YIQ-based; its current README says OKLab HyAB ("A perceptual color space for image processing", 2020). The YIQ description is outdated for pixelmatch ≥7; odiff itself still uses YIQ. Checked both repos directly.
- Playwright's test-snapshots page does not actually recommend Docker; the Docker-bless recommendation lives in community posts. The docs' verified claim is only "run tests in the same environment where the baseline screenshots were generated". The docker docs page (playwright.dev/docs/docker) describes how, not why.
- jest-image-snapshot's README contains nothing about cross-platform font rendering or Docker, contrary to the common framing of it as the tool that "solves" that problem.
- zlib FAQ checked for a determinism guarantee: none exists (only cross-architecture interoperability, FAQ #25). Ruled out as a source of byte-stability assurance.
- https://freetype.org/freetype2/docs/subpixel-hinting.html is a 404; the live page is under /docs/hinting/subpixel-hinting.html.
- insta's "advanced features" page does not cover binary snapshots; they are documented on the snapshot-types page (byte-for-byte, experimental).
- GitHub's LFS billing docs pages do not state per-GiB overage prices; only the changelog/community posts carry the $0.07 / $0.0875 figures.
- matplotlib.org/stable/devel/testing.html returned 403 to direct fetch; evidence taken from the versioned 2.1.0 docs URL and the repo issue/PR instead.
- No embedded instructions were found in any fetched page content.
