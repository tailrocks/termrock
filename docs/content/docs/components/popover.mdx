## State and typed outcomes

`PopoverState` owns open/focus/presentation state and slot geometry. Overlay placement and opener focus remain host-owned; the demo reports the close reason without external effects.

## Usage

The Code view above and this source excerpt use the exact paint setup registered for `popover/basic`. Interaction state is long-lived in the catalog interactor; the host only forwards backend-neutral events.

```rust
use ratatui::prelude::*;
use termrock::{input::*, interaction::*, runtime::*, style::*, widgets::*};

// Exact paint setup used by the shared catalog story.
fn popover_story(frame: &mut Frame<'_>, area: Rect, system: &DesignSystem) {
    let mut state = popover_open_state();
    Popover::new("Settings", system).paint(area, frame.buffer_mut(), &mut state);
    // Host paints body content into slots (not forced Panel).
    let body = state.slots().body;
    if !body.is_empty() {
        frame.buffer_mut().set_stringn(
            body.x,
            body.y,
            "filter · sort · density",
            usize::from(body.width),
            system.style(termrock::style::Role::Text),
        );
    }
}
```

## Common mistakes

- Do not treat separate Lookbook stories as runtime states or a slide sequence.
- Do not duplicate hit testing, focus, or keyboard rules in the host.
- Do not infer an action from visual styling; handle the widget's typed outcome.
