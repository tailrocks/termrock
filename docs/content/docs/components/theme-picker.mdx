This preview mounts one persistent Rust state machine. Focus it, use the current actions shown by the runtime, inspect the typed outcome, and use **Reset** for fresh state.

## Try it

- `arrow keys`: Move through the real focus/selection model; the next action uses the new target.
- `Enter activate`: Activate the focused or pointed target; inspect the changed cells and typed outcome below the terminal.
- `click`: Activate the focused or pointed target; inspect the changed cells and typed outcome below the terminal.

Every accepted action reaches the same mounted Rust value. The status line shows the latest typed outcome; **Reset** creates a fresh instance.

## State and typed outcomes

The demo owns ephemeral widget state between events. The widget owns painted geometry, focus/selection mechanics, and typed outcomes. The host owns domain effects and decides what an emitted outcome means to the application.

## Usage

The Code view above and this source excerpt use the exact paint setup registered for `system-picker/basic`. Interaction state is long-lived in the catalog interactor; the host only forwards backend-neutral events.

```rust
use ratatui::prelude::*;
use termrock::{input::*, interaction::*, runtime::*, style::*, widgets::*};

// Exact paint setup used by the shared catalog story.
fn theme_picker(frame: &mut Frame<'_>, area: Rect, system: &DesignSystem) {
    let mut state = ThemePickerState::new(0);
    frame.render_stateful_widget(
        &ThemePicker::new(BUILTIN_THEME_PRESETS, system),
        area,
        &mut state,
    );
}
```

## Common mistakes

- Do not treat separate Lookbook stories as runtime states or a slide sequence.
- Do not duplicate hit testing, focus, or keyboard rules in the host.
- Do not infer an action from visual styling; handle the widget's typed outcome.
