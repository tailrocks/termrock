## Try it

- `←→ adjust`: Dispatch this action to the mounted Rust state machine and inspect its visible typed result.
- `Home/End`: Move through the real focus/selection model; the next action uses the new target.
- `drag track`: Press, drag, and release on the visible handle; geometry/value follows the pointer.
- `wheel over slider`: Scroll over the preview; its own viewport moves while the docs page stays put.

Every accepted action reaches the same mounted Rust value. The status line shows the latest typed outcome; **Reset** creates a fresh instance.

## State and typed outcomes

The demo owns ephemeral widget state between events. The widget owns painted geometry, focus/selection mechanics, and typed outcomes. The host owns domain effects and decides what an emitted outcome means to the application.

## Usage

The Code view above and this source excerpt use the exact paint setup registered for `slider/basic`. Interaction state is long-lived in the catalog interactor; the host only forwards backend-neutral events.

```rust
use ratatui::prelude::*;
use termrock::{input::*, interaction::*, runtime::*, style::*, widgets::*};

// Exact paint setup used by the shared catalog story.
fn slider_basic_story(frame: &mut Frame<'_>, area: Rect, system: &DesignSystem) {
    let mut state = SliderState::new(62.0);
    state.set_focused(true);
    let _ = Slider::new(SliderBounds::percent(), system)
        .label("Volume")
        .paint(area, frame.buffer_mut(), &mut state);
}
```

## Common mistakes

- Do not treat separate Lookbook stories as runtime states or a slide sequence.
- Do not duplicate hit testing, focus, or keyboard rules in the host.
- Do not infer an action from visual styling; handle the widget's typed outcome.
