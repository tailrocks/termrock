## Live terminal (Ghostty-class)

This preview mounts one persistent Rust state machine. Focus it, use the current actions shown by the runtime, inspect the typed outcome, and use **Reset** for fresh state.

<TerminalPreview story="task-rail/basic" interactive caption="TaskRail · Task rail — live shared Rust state" />

## Try it

- `↑↓ select`: Move through the real focus/selection model; the next action uses the new target.
- `←→ collapse/expand`: Dispatch this action to the mounted Rust state machine and inspect its visible typed result.
- `/ filter`: Focus the editable field, then type or paste Unicode text; the draft remains visible.
- `Enter activate`: Activate the focused or pointed target; inspect the changed cells and typed outcome below the terminal.

Every accepted action reaches the same mounted Rust value. The status line shows the latest typed outcome; **Reset** creates a fresh instance.

## Usage

The Code view above and this source excerpt use the exact paint setup registered for `task-rail/basic`. Interaction state is long-lived in the catalog interactor; the host only forwards backend-neutral events.

```rust
use ratatui::prelude::*;
use termrock::{input::*, interaction::*, runtime::*, style::*, widgets::*};

// Exact paint setup used by the shared catalog story.
fn task_rail_story(frame: &mut Frame<'_>, area: Rect, system: &DesignSystem) {
    use termrock::patterns::{TaskRail, TaskRailState, example_activity_models};
    let items = example_activity_models();
    let mut st = TaskRailState::new();
    st.focused = true;
    st.list.select(Some("p1".into()));
    TaskRail::new(&items, system)
        .title("Tasks")
        .paint(area, frame.buffer_mut(), &mut st);
}
```

## Common mistakes

- Do not treat separate Lookbook stories as runtime states or a slide sequence.
- Do not duplicate hit testing, focus, or keyboard rules in the host.
- Do not infer an action from visual styling; handle the widget's typed outcome.
