# CI

CI is generated by `velnor-gen` (<https://github.com/tailrocks/velnor-new>,
tag `tools-v0.1.111`) from `.velnor/rust-ci.toml`. Never hand-edit
`.github/workflows/rust-ci.yml`, `.velnor/rust-metadata.json` or
`.velnor/rust-ci.lock`. Change the config and run:

```sh
git add .velnor/rust-ci.toml        # velnor-gen refuses an untracked config
mise exec -- velnor-gen generate    # rewrite the generated files
mise exec -- velnor-gen check       # exit 1 when a generated file is stale
```

`velnor-gen pin-helper <version>` writes `.velnor/rust-ci.lock`, which pins the
run-time helper `velnor-ci` (and the digests of every release asset). The
configuration reference is `generator/CONFIG.md` in velnor-new and the
behaviour is described in its `docs/rust-ci.md`. Every decision is recorded in
[decisions](decisions.md) under "CI moves from velnor-actions to velnor-gen".

## Jobs

The workflow is `Rust CI` (`rust-ci.yml`) and runs on pull requests, pushes to
`main`, the merge queue, a nightly schedule and manual dispatch. The generator
makes one job set per Cargo root, not one job per crate. The repository has five
roots: the workspace at `.` and the four consumer fixtures.

- **rust-plan** — `velnor-ci plan` selects the packages a run must test from
  the diff, and everything on a schedule, a manual run or a change to a
  toolchain, Cargo or mise file.
- **rust-lint-root** — `cargo fmt --check`, `cargo clippy --workspace
  --all-targets -D warnings` and `cargo doc` (rustdoc warnings denied) with the
  default features, and one `Check <crate> alone` step per workspace member
  (`cargo check -p <crate>`, default features only, warnings allowed).
- **rust-test-root** — builds the default-feature nextest archive once, then
  runs the *all-features lane* (below): tests, clippy and rustdoc with
  `cli,demo,product,terminal,test-support,work-metrics`. This job is where the
  `work-metrics` cost contracts of #56 execute; see [performance contracts](performance-contracts.md).
- **rust-test-default-root** — every test no group names, from the archive,
  under the `ci` nextest profile.
  The `settle` nextest setup script (`scripts/nextest-settle.sh`) runs before
  the first test of every archive run in CI and waits for velnor-ci's early
  `nextest list` to exit. That list repeats the run's `--extract-to .
  --extract-overwrite` (tailrocks/velnor-new#2402, #2361) and rewrites the test
  binaries that are already being launched, which failed 44 tests with
  `[double-spawn] failed to exec ... Permission denied` in run 44791274299.
  Delete the script when velnor-ci stops re-extracting.
- **rust-test-cargo-tools-root** — the three tests that run `cargo metadata`
  (`jackin-console::product_manifest::manifest_shape`,
  `termrock::regressions::layering::{layering_crates_follow_the_table,layering_stage_b_runs_on_the_extracted_crates}`).
  The default job has no Rust toolchain, so this `[[test_groups]]` entry
  (`needs = ["cargo"]`) runs them and the default job leaves them out. A new
  test that shells out to `cargo` belongs in this group's filter.
- **termrock-catalog gate** — the declared-API gate of #14 (`catalog_` tests in
  `termrock-catalog`, which hold the committed id digest and the
  `doc-hidden-items.txt` list). It runs in the all-features lane. Its command with
  the Showcase scenarios is `cargo nextest run -p termrock-catalog -p
  termrock-showcase --all-features --no-tests fail -E 'test(catalog_)'`.
- **rust-test-functional-{cases-a,cases-b,cases-c,apps}-root** — the
  `functional` binaries (`termrock-functional`, `functional-cross`,
  `jackin-console`), 1,371 PTY tests, split into four disjoint
  `[[test_groups]]` of 317 to 384 tests that run from the archive with eight
  test threads and a 30-minute limit each. They replace the four hash
  partitions of the old `Suite (functional)`. `cases-a` is `g05`, `h01`-`h06`
  and `s01`-`s03`, `cases-b` is `s04`-`s07`, `cases-c` is `s08`-`s10`, `t01`-`t05`,
  `x01` and `x02` plus `functional-cross`, and `apps` is the `showcase`,
  `tablepro`, `holla`, `lifecycle` and `visual` tests of `termrock-functional`
  plus `jackin-console`. `velnor-ci test-groups check` fails the build job if
  two groups select one test. A functional test that no group names (a new
  `cases::` prefix) runs in `rust-test-default-root`, so add its prefix to a
  group. Each group needs `cargo` because the nextest setup script `app-bins`
  builds the app binaries the journeys launch. See
  [functional testing](functional-testing.md).
- **rust-crates_termrock_tests_consumers_{minimal,keyed_modal,terminal,jackin_host}**
  — the four independent consumer fixtures under
  `crates/termrock/tests/consumers/`. Each is its own Cargo workspace with a
  committed lockfile, so velnor-gen treats it as its own root and builds it
  from its own directory with the features it declares alone. They are the CI
  gate for the feature contract of [API contract](api-contract.md) and the
  only place the library shapes without default features (`minimal`,
  `terminal`, `jackin-host`) are built. `bash scripts/check-consumers.sh` runs
  the same four locally and also checks each normal dependency tree.
- **lint-crates-alone** — the mise task `check-crates-alone`: every workspace
  member on its own (`cargo clippy --package <member> --all-targets -D
  warnings`), once with default features and once with `--all-features`, plus
  `termrock` with `--no-default-features --features terminal`
  (the former `product` shape). A
  workspace build unifies features across members, so a member that misses a
  feature forward (the #446 `work-metrics` defect) or leaves an import unused
  when a consumer leaves a feature off builds there and fails only alone. The
  generated `Check <crate> alone` steps cannot catch either: they run
  `cargo check` with default features and no `-D warnings`. This job is the
  replacement for the 27 per-crate `--all-features` jobs on that point. It
  has no cache, so it compiles from scratch.
- **lint-jactionlint** — jactionlint (with ShellCheck) over the workflows,
  configured by `.github/jactionlint.yaml`.
- **lint-generated-workflows** — runs `velnor-gen check` (the mise task
  `check-generated-workflows`), so a stale or hand-edited generated file fails
  the pull request. See [Generated workflow check](#generated-workflow-check).
- **rust-trim** — "Cache maintenance", on the default branch only: prunes
  superseded caches towards the budget.
- **required** — the check named **Required**. It passes only when every
  selected job ran and passed. Require this one check in the ruleset; its name
  is unchanged from the velnor-actions workflow, so a ruleset that requires it
  keeps working. No ruleset requires it yet; it is created at rename time.
- **cache** — the advisory cache report.
- **DCO** — every commit must carry `Signed-off-by` (`git commit -s`, committer
  Alexey Zhokhov <alexey@zhokhov.com>). It is a GitHub app, not a workflow, and
  is unaffected by the generator. SonarCloud runs as Automatic Analysis
  (`.sonarcloud.properties`), also not a workflow.

## The all-features lane

velnor-gen builds with the default features and has no `--all-features` flag.
The `[[test_lane]]` entry of `.velnor/rust-ci.toml` re-runs the selected tests,
clippy and rustdoc with every feature named. The list must hold every feature
of every workspace member (`cli`, `demo`, `product`, `terminal`, `test-support`,
`work-metrics`); add a new feature there when a crate declares one. The lane
selects every test except the `functional` binaries (`not binary(functional)`),
which run in the test groups, as the old `ci` nextest profile did for the
per-crate jobs. A `Test lane guard` step (`velnor-ci lane-guard`) fails the job
if a test that exists only with those features falls outside the filter. None
does today, and none is a functional test.
`tests/regressions/performance_inventory.rs` pins that the lane exists, carries
no other filter, names every package and that `Required` waits for its job.

The old `product` configuration (`--no-default-features --features product`,
run for `termrock` and `jackin-console`) is not generated. `product`
gates no code: it is an alias of `terminal`. For `jackin-console` it is empty
and `default = []`, so the default build is the same build. For `termrock` and
the shape is `terminal` without `cli`; `lint-crates-alone` builds
it with `--no-default-features --features terminal` under `--all-targets`, and
the `termrock-consumer-terminal` and `termrock-consumer-jackin-host` fixtures
build the library code of that shape as consumers.

## Test targets and generated CI

`.velnor/rust-metadata.json` records every workspace member, dependency and
test target. `velnor-ci check-metadata` fails each job when it differs from
`cargo metadata`, so a new test target, dependency or feature needs
`velnor-gen generate` in the same change. Two pull requests that each add a
target conflict in that file, which must never be resolved by hand: rebase,
run `velnor-gen generate` and commit the result.

New integration tests go into the shared `regressions` target of their
package, which keeps the target list stable:

- Every library crate: `crates/<crate>/tests/regressions/<topic>.rs` plus
  `mod <topic>;` in that crate's `tests/regressions/main.rs`. A test goes to the
  highest crate it imports, and to `crates/termrock` when it needs the facade
  paths or several sibling crates. There is no root `tests/` directory.
- `termrock-conformance`: `crates/termrock-conformance/tests/regressions/<topic>.rs`
  plus `mod <topic>;` in its `main.rs` (the cost contracts of #56, the inventory
  gate and the default-branch guard).
- `jackin-console`: `apps/jackin/tests/regressions/<topic>.rs` plus
  `mod <topic>;` in `apps/jackin/tests/regressions/main.rs` (the target is
  gated by the `demo` feature).

Add a new top-level `crates/<crate>/tests/*.rs` only when a test needs its own binary
(different features, harness or process-wide state), and regenerate in the
same change.

`crates/termrock-conformance/tests/regressions/ci_default_branch.rs` checks offline that `default_branch` in
`.velnor/rust-ci.toml` is set explicitly to `main` and that the generated
workflow pushes only that branch. To change the branch, edit the key, run
`velnor-gen generate` and confirm a second `velnor-gen check` passes.

The key is explicit because velnor-gen 0.1.111 accepts it at the top level of
`rust-ci.toml` and falls back to `main` when it is absent. The guard does not
inherit that fallback: an absent key, or any value other than `main`, fails the
test. The guard also fails when the generated `push` trigger lists a branch
other than `main`, lists none, or when the branch list is missing.

Decision (issue #13, re-audit after the velnor-gen migration of #559): the
original spec required the default branch to be explicit and a missing key to
fail (exit 2 in the first validator). The velnor-actions `.velnor/config.toml`
(`[workflow].default_branch`) was removed by the migration, and the replacement
`rust-ci.toml` had no key, so a missing key passed silently. The fix restores
the explicit key and makes the guard reject its absence again.

## Generated workflow check

`velnor-gen check` exits 1 when `.github/workflows/rust-ci.yml` or
`.velnor/rust-metadata.json` differs from what `generate` would write. It runs
in two places:

- locally, as the `generated-workflows` step of the hk `pre-commit` and
  `pre-push` hooks (`hk.pkl`). Install the hooks once with
  `mise exec -- hk install`. The pre-push hook checks the tree at `HEAD`, not
  every pushed commit.
- in CI, as the `lint-generated-workflows` job, which `Required` waits for. A
  bypassed or missing hook is therefore caught on the pull request.

`velnor-gen` comes from `mise.toml`: a source build of the commit of tag `tools-v0.1.111` on
macOS (the tools release has no macOS asset) and the prebuilt release asset on
Linux, with its checksum in `mise.lock`. `tests/ci_default_branch.rs` pins the
`version` and `commit` of `.velnor/rust-ci.lock` to those pins, because
`velnor-gen check` does not compare them, and pins `[velnor-gen].linux-x64` to the
archive checksum in `mise.lock`. `velnor-gen pin-helper` writes both: `[velnor-gen]`
holds the archive digest and `[velnor-gen-binary]` holds the digest of the extracted
binary (`BINARY-SHA256SUMS`). On Linux `velnor-gen check` compares `[velnor-gen-binary]`
with the running binary. Run `pin-helper` and do not edit the digests by hand. The
generator reads the checkout's own `mise.toml`, so the check proves reproducibility,
not authorization.

Git sources in `Cargo.lock` disable the base caches unless they are declared.
`.velnor/rust-ci.toml` lists `termpane` and `tuiscotti` under `[public_sources]`,
both public repositories. A new git dependency that is private needs a
`[private_sources]` entry instead. The base caches save on pushes to `main` only.

## Workflow policy boundary

The `lint-generated-workflows` job establishes reproducibility; it does not
authorize changes to `.velnor/rust-ci.toml`, `.velnor/rust-ci.lock` or the
generated workflow. Local hooks can be absent or bypassed, and a branch can
change its own workflow before CI evaluates it. The helper pin is the small
reviewable trust anchor: `.velnor/rust-ci.lock` holds the digest of every
`velnor-ci` asset, so a change to the helper is a visible lock change. GitHub
settings inspection on 2026-11-06 found no branch-protection rule and no
repository ruleset requiring a trusted workflow. The repository owner must
configure a required trusted workflow or ruleset for server-side enforcement.
Until then, workflow-source and policy changes need trusted review.
