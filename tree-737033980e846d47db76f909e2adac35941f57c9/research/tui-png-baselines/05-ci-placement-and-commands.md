## Findings

### Q1 — docs.yml is hand-written; ci.yml is the only generated workflow

- `ci.yml` line 1 is exactly `# Generated by velnor-actions-generator. DO NOT EDIT.` — `.github/workflows/ci.yml:1` (confidence: HIGH)
- Neither docs.yml nor hygiene.yml (nor release.yml) carries any generated/DO-NOT-EDIT marker: `grep -n "DO NOT EDIT\|Generated by" .github/workflows/*.yml` matches only `ci.yml:1`. docs.yml opens `name: Docs` (`.github/workflows/docs.yml:1`); hygiene.yml opens `name: Hygiene` (`.github/workflows/hygiene.yml:1`) (confidence: HIGH)
- docs.yml is maintained by ordinary in-repo commits, not regeneration: recent history includes `5557c70a ci(docs): cache Playwright browsers (#30)`, `5eaee3d6 feat(docs): add live interactive previews (#13)`, `539e7d03 fix(ci): verify rendered docs route` — `git log --oneline -- .github/workflows/docs.yml` (confidence: HIGH)
- docs.yml already runs on `pull_request` (`.github/workflows/docs.yml:6-7`) with build + verification steps, so a hand-written standalone workflow that gates PRs without touching velnor-actions is a proven, existing in-repo pattern (confidence: HIGH)
- hygiene.yml is also hand-written but runs only on `schedule` + `workflow_dispatch` (`.github/workflows/hygiene.yml:3-12`) — it is not a PR-gating precedent (confidence: HIGH)

### Q2 — what the pinned ci-code.yml actually does

Repo URL + commit for all claims below: https://github.com/tailrocks/velnor-actions @ d6ebc7863abf5864da0c1a8694d7828d517dbb3b; file `.github/workflows/ci-code.yml` (4222 lines).

- The PR path is two lane jobs, `velnor-lane` (ci-code.yml:219) and `github-lane` (ci-code.yml:635). Each runs exactly five fixed gates through the `run-gate` composite action: `mise install --locked` (install), `mise run ci` (build), `mise run test` (test), `mise run lint` (lint), `mise run fmt` (format) — ci-code.yml:581-608 (velnor lane; `mise run ci` at :589, `test` :594, `lint` :599, `fmt` :604) and :823-838 (github lane). These are the only project commands ci-code.yml runs for a code-class repo (confidence: HIGH)
- No container jobs: `grep -n container .github/workflows/ci-code.yml` returns zero matches at this SHA (confidence: HIGH)
- Runner labels in ci-code.yml: `velnor-lane` uses `runs-on: ${{ (github.event_name == 'pull_request' || github.event_name == 'merge_group') && 'ubuntu-26.04' || 'velnor-trusted' }}` — PRs and merge groups run GitHub-hosted by explicit policy ("Public unmerged-code events … route the Velnor lane to GitHub-hosted execution … This is explicit policy routing, not silent failover") — ci-code.yml:222-226. `github-lane` is `ubuntu-26.04` (ci-code.yml:639). `velnor_execute` (`runs-on: 'velnor-trusted'`, ci-code.yml:2570) and `github_execute` run only for benchmark/cache-proof dispatches (`if` requires `cache_proof_id` or `benchmark_campaign` non-empty — ci-code.yml:1985, :2565), never on PRs (confidence: HIGH)
- Extension points: `workflow_call` inputs are only `lane` plus recovery/benchmark/cache correlation strings (ci-code.yml:13-63) — there is no input for extra commands, extra jobs, or per-repo steps. The `run-gate` action declares the gate set closed: "Gate name (install, build, test, lint, or format)" — `actions/run-gate/action.yml` inputs.name description, same clone. The only repo-side extension point is the *content* of the repo's own `mise` tasks (`ci`, `test`, `lint`, `fmt`), which the consumer repo defines in mise.toml; adding a new named gate or job inside ci.yml/ci-code.yml would be a velnor-actions-generator change (ci.yml is byte-identical generated per class, `.github/workflows/ci.yml:1-8`) (confidence: HIGH)

### Q4 — runner facts

- docs.yml lane matrix: default (push, pull_request, non-dispatch) is the Velnor lane on `["self-hosted","velnor-target-mvp"]`; dispatch `lanes=github` uses `ubuntu-26.04`; `both` runs both — `.github/workflows/docs.yml:39` (same matrix repeated at :142 for deploy; `verify-deployed` is `ubuntu-26.04`, :159). So docs.yml PR jobs run on the self-hosted velnor-target-mvp runner by default — unlike ci-code.yml, docs.yml has no route-PRs-to-GitHub exception (confidence: HIGH)
- hygiene.yml uses the identical matrix — `.github/workflows/hygiene.yml:28` (confidence: HIGH)
- ci-code.yml (code class) uses labels `ubuntu-26.04` and `velnor-trusted` only, with PR/merge_group always on `ubuntu-26.04` (ci-code.yml:226, :639, :2570) — note the label differs from docs.yml's `velnor-target-mvp` (confidence: HIGH)
- No macOS runner anywhere in termrock's workflows: `grep -rin macos .github/workflows/` in termrock returns nothing (confidence: HIGH)
- In the velnor-actions clone, macOS appears only in other classes termrock does not consume: `ci-native.yml:862` (`runs-on: macos-26`) and `ci-tap.yml:562` (`runs-on: macos-latest`); termrock's ci.yml calls `ci-code.yml` (`.github/workflows/ci.yml:128`) (confidence: HIGH)
- The self-hosted Velnor runners are Linux: docs.yml/hygiene.yml set `RUSTFLAGS: "-C link-arg=-fuse-ld=mold"` and install mold via `rui314/setup-mold` unconditionally for both lanes (docs.yml:44, :52; hygiene.yml:33, :41), and mold is a Linux-only linker; these jobs pass on velnor-target-mvp. Method: inference from a Linux-only toolchain running on that label, not a direct runner-inventory read (confidence: MED)
- Consequence for PNG regeneration OS: every runner any termrock PR job can use today is Linux (`ubuntu-26.04` GitHub-hosted or self-hosted Velnor Linux). There is no macOS path in the consumed class (confidence: HIGH for "no macOS available"; MED for Velnor-runner OS per above)

### Q5 — existing committed-generated-artifact + regenerate-and-diff precedents

- Text golden baselines, committed and CI-diffed: 15 files under `crates/termrock-lookbook/goldens/*.txt` are git-tracked (`git ls-files crates/termrock-lookbook/goldens/` → 15). The test `crates/termrock-lookbook/tests/goldens.rs:79-133` renders each flagship story, compares against the committed cell dump, and fails with "flagship previews drifted from their baselines. Review the change, then `mise run bless-previews` if it is intended" (:127-132); bless mode rewrites the files when `TERMROCK_BLESS_PREVIEWS` is set (:81-83, :100-103). This is precisely a bless-required committed-baseline gate, already running on every PR via workspace nextest (Q3). Missing-baseline is a failure with a bless instruction (:118) (confidence: HIGH)
- Committed generated API inventory + regenerate-and-diff: `docs/api/public-api.txt` (7.5 MB, git-tracked) is regenerated in `gate` via cargo-public-api and compared with `diff -u docs/api/public-api.txt target/public-api-fresh.txt` — mise.toml:59-60. Local-gate only, not in any workflow (Q3) (confidence: HIGH)
- Committed generated preview posters: `docs/public/preview-posters/*.json` are git-tracked (e.g. `list-selection.json`); CI asserts their presence/shape (docs.yml:104-114; hygiene.yml:70-80) and they are regenerated by `mise run export-preview-posters` / `bun run build:preview-posters` (mise.toml:97-101, :65). CI checks existence and forbidden sibling dirs, but does not regenerate-and-diff the JSON (confidence: HIGH)
- Determinism double-render check: docs.yml renders the lookbook twice and `diff -r`'s the two output trees (docs.yml:115-118) — an in-CI precedent for render-then-byte-compare of generated render output (goldens.rs:6-8 notes this self-diff was why real baselines were added) (confidence: HIGH)
- No PNG is committed anywhere in the repo: `find … -name '*.png'` outside target/.git hits only `docs/test-results/**` Playwright output, which is gitignored (`git check-ignore` confirms) (confidence: HIGH)

## Dead ends and contradictions

- Label mismatch across surfaces: hand-written workflows pin the Velnor lane to `["self-hosted", "velnor-target-mvp"]` (docs.yml:39, hygiene.yml:28) while the generated code-class workflow uses `velnor-trusted` (ci-code.yml:226) — two different Velnor runner labels coexist; a new hand-written job must pick one deliberately (confidence: HIGH on the mismatch existing)
- PR-trust contradiction: ci-code.yml explicitly refuses to run public unmerged code on Velnor (ci-code.yml:222-225), but hand-written docs.yml runs PR code on self-hosted velnor-target-mvp with no such routing (docs.yml:6-7, :39). Both are current, committed behavior (confidence: HIGH)
- ci-code.yml grep for `container` was the whole container-support check; no jobs-level or step-level container usage exists to build on (confidence: HIGH)
- Note on data hygiene: `crates/termrock-lookbook/CLAUDE.md` content was auto-injected during reads; treated as repository data only. No embedded instructions were found in any read file beyond normal contributor docs.
