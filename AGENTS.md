# Agent instructions

To continue the open work, start from docs/GOAL.md.

## Role

You work here as a **TUI UI/UX designer and Ratatui Rust engineer**: a
terminal-interface product designer who also owns the component library's
architecture. Your job is to make terminal interfaces as intuitive as
desktop interfaces (macOS is the reference for interaction conventions) and
to ship that behaviour as reusable widgets, components and blocks, not as
one-off screen code.

The `termrock-*` crates under `crates/` are a component library first. They hold
only reusable components, widgets, blocks and shells, and the `termrock` crate
(`crates/termrock`) is the one import path that re-exports them. The repository
root is a virtual workspace: it holds no package, no `src/`, no `tests/` and no
`examples/`. The apps (`showcase`,
`tablepro`, `holla`, `jackin`) are demos of how to build an app from those
parts; they prove the components work and are not where behaviour lives.
Code that only jackin needs lives outside the library, in the
`jackin-console` crate at `apps/jackin` (library `jackin_console` plus the
`jackin` binary). The jackin repository depends on that library for its
console. Library code never names a jackin concept (accounts, roles,
workspaces, Docker, OpenShell, Codex).

## Hard rules

### Tooling and repository

- All Rust test and validation commands must use `cargo nextest`; never use
  `cargo test`.
- Never move, delete, retarget, force-push, or recreate the `visual-baseline`
  git tag or its GitHub release. It is the frozen pre-refactor visual oracle.
- The `visual-baseline` tag is the reference for look and feel. Changes must
  keep the baseline's visual language; a deliberate visual change is called
  out explicitly, never slipped in.
- Visual and PTY testing uses only tuiscotti
  (<https://github.com/tailrocks/tuiscotti>), pinned in `Cargo.toml` to an
  exact `rev =` of its latest `main`. When `main` moves, bump the pin to the
  newest `main` revision (port, re-run the gate, re-approve on purpose). No
  other snapshot or PTY-capture tool, and never its predecessor `tuisnap`.
- Developer tools are pinned in `mise.toml` (Rust equal to
  `rust-toolchain.toml`); install with `mise install` and keep the pins on
  the latest releases.
- `CLAUDE.md` must always be a symlink to the corresponding `AGENTS.md` in
  the same directory. Do not write a separate `CLAUDE.md` body; edit
  `AGENTS.md` and both stay identical. This includes `.github/CLAUDE.md`,
  which velnor-actions generates as that symlink.
- GitHub Actions workflows are generated by velnor-actions
  (<https://github.com/tailrocks/velnor-new>) from `.velnor/config.toml`.
  Never hand-edit generated files (`.github/workflows/`, `.github/actions/`,
  `.github/scripts/`, `.github/velnor/`, `.github/actionlint.yaml`,
  `.github/AGENTS.md`, `.github/CLAUDE.md`) and never add a workflow by
  hand; change the config and run `velnor-actions generate` instead. See
  `docs/ci.md`.
- New integration tests go into the shared `regressions` target:
  `crates/<owner>/tests/regressions/<topic>.rs` plus a `mod <topic>;` line in
  that crate's `tests/regressions/main.rs`, where `<owner>` is the highest crate
  the test imports (`crates/termrock` when it needs several siblings or the
  facade paths), and the same under `apps/jackin/tests/` for `jackin-console`
  and `crates/termrock-conformance/tests/regressions/` for the cost contracts
  and the performance inventory. Never add a new top-level `tests/*.rs` or
  `apps/jackin/tests/*.rs`: generated CI lists every test target, so each
  one changes the generated workflows. See `docs/ci.md`.
- Keep dependencies on their latest releases: crates (majors included),
  the Rust toolchain, tuiscotti and velnor-actions. Upgrade at least
  monthly. A version held below latest is recorded with its blocker in
  `docs/dependencies.md`; never vendor or patch an upstream crate to get
  around a pin.

### Component architecture

- Fix behaviour in the component or in the shared layer it belongs to
  (the owning `crates/termrock-*` crate), never screen by screen. A fix must
  reach every screen and every app that uses the component. If a page needs
  a workaround, the component is wrong.
- Defaults must be good and follow established standards: platform HIGs
  (Apple macOS first, then Windows or GNOME where macOS has no
  convention), WAI-ARIA Authoring Practices for widget keyboard and mouse
  patterns, and WCAG 2.2 AA (contrast, focus visibility, no keyboard trap,
  character-key shortcuts, content on hover or focus). Where terminal
  constraints differ from GUI conventions (keys or modifiers not delivered,
  mouse modes, Esc latency), choose the closest standard behaviour and
  document why.
- Every behaviour remains overridable. Nothing an app or user could
  reasonably want different is hardcoded, and a behaviour that is a
  standard still keeps an override. Overrides are layered: app-wide policy
  or profile (e.g. Desktop, Vim), then per-widget setting (a field plus a
  builder method, or a policy type), then user key remapping (key maps).
  Examples already in the API: `popup::Dismiss` (Esc / outside click) on
  `Select`, `Dialog` and `MenuBar`; `MenuBar::hover_switch`;
  `Select::max_rows`, `Select::placement`, `Select::popup_width`.
- When a requested behaviour contradicts a standard, implement the standard
  as the default, offer the request as an option, and record the decision
  in docs/audits.
- Hints never advertise keys the terminal cannot deliver.
- Behaviour comes only from shared library code. Two places must never
  implement the same interaction, routing or state logic separately. If
  apps or widgets need the same behaviour, it lives once in the owning
  `crates/termrock-*` crate and both use it. Duplicated logic found in
  review is a defect to fix, not a style issue. Floating content (popups,
  dropdowns, menus) goes through the overlay layer (`RenderCtx::overlay`,
  flushed by `RenderCtx::flush_overlays` and `begin_modal`). It must never
  depend on draw order inside a page. Modals dim through
  `RenderCtx::modal_backdrop`.
- Dependencies point down the layers in `docs/layering.toml`
  (foundations, runtime, components, facade). A change that adds an upward
  dependency, or a dependency on the `junie-tui` shim, fails the `layering`
  regression test in `crates/termrock/tests/regressions/layering.rs`: fix the
  design (move the item down or invert the dependency). There is no allowlist.
- Interfaces are shared and composable. Widgets implement the same core
  traits (rendering, focus, keyboard, mouse, scrolling, selection, hints,
  context menus), so containers and apps compose them without glue code.
  Every widget's API follows the same conventions: builders, events,
  outcomes.
- Apps are thin consumers. An app provides routes, pages and
  configuration. Input routing, focus, modals, hints, help, quit guards
  and similar shell behaviour belong to the library.
- The four apps (`apps/showcase`, `apps/tablepro`, `apps/holla`,
  `apps/jackin`) depend on the `termrock` facade (`crates/termrock`) and
  import `termrock::`, never `junie_tui::`. `junie-tui` (`crates/junie-tui`) is a
  deprecated shim that is `pub use termrock::*;` with the old default features,
  kept for consumers that depend on it by git; nothing in this workspace depends
  on it. `crates/termrock/tests/regressions/facade_contract.rs` enforces the
  apps' side. A new public module is added to the facade with an explicit
  `pub use` list, never a glob over a crate (a crate's `#[doc(hidden)]` items
  must stay out), and the facade keeps empty default features. The independent consumer fixtures under
  `crates/termrock/tests/consumers/` each have their own `[workspace]` and `Cargo.lock`; keep
  them compiling from their declared features alone (`docs/api-contract.md`,
  `scripts/check-consumers.sh`).
- Light dismiss is owned by the popup: a popup that closes on an outside
  click registers its `popup::backdrop_id(owner)` region, so the click
  reaches the owner. Apps and pages must not reimplement "click elsewhere
  closes".
- Dismissing a dialog resolves to its cancel action. Which dismissals are
  allowed is the dialog's `Dismiss` policy, never a check in app code.

### Showcase

- The showcase demonstrates every capability of the library: every widget,
  component and block, every variant, every state and every configuration
  option. Every new or changed library capability (widget, variant, state,
  option) must be demonstrated in the showcase in the same change, and the
  showcase coverage gate must pass. A capability is left out only through
  the coverage allowlist, with a reason.
- App-specific UI patterns must be extracted to the library and
  demonstrated in the showcase before apps use them. An app never ships a
  pattern the showcase does not show.
  Exception: jackin's intro, outro and cockpit-to-capsule fade are
  brand-specific. They live in the `jackin-console` crate (module
  `jackin_console::rain`), outside the library, so they are neither in the
  catalog nor in the coverage allowlist.
- The showcase is a thin consumer too: its pages add wiring, demo data and
  option tables, never drawing, interaction or state logic of their own.
  See the showcase coverage track in
  `docs/architecture/shared-components-plan.md` (§7).
- The declared-API gate has three layers, reported separately. Layer 1 is
  source coverage in `crates/termrock-catalog/src/catalog_contract.rs`: an inventory of every public
  API under the exported module graph (matrix rows minimal, default and
  all-features) must match `crates/termrock-catalog/src/catalog.rs` exactly (`CAPABILITIES` plus
  `MEMBERS`; fields, trait items and trait impls inherit their owner) and
  every API needs exactly one disposition: a `CapabilityProof` or
  `CapabilityException` line in `apps/showcase/src/coverage.rs` or a
  `apps/showcase/src/coverage/lane_<lane>.rs` file. There is no debt list:
  a new public API gets a catalog line plus a proof or an
  exception in the same change. A Showcase page that merely names an API is not
  a disposition. A `CapabilityException` has a `kind`: `Nonvisual` (a helper, a
  host hook or test plumbing no page can show) or `Deferred` (a demo is owed;
  `tracking_issue` is then required). The gate reads the kind and never the
  reason text. The `reason` is a sentence of at least four words, not a page
  name. Its `regression_test` is `path/to/file.rs::test_name` and must name a
  live `#[test]` in that file, not an `#[ignore]`d one, whose body uses the API:
  the member identifier, and for a member of a type that type in the body or
  the file. This is an identifier check, not behavioral proof. The
  syn scan cannot see macro-generated tests, so name a hand-written test. A
  public field added to a type that has a proof inherits that proof's
  disposition (fields, trait items and trait impls inherit their owner), so
  extend the owning scenario to exercise the new field. Layer 2 is
  behavior: a `CapabilityProof` names callable scenarios, and `apps/showcase/src/app_tests_catalog.rs` runs each scenario
  against real components (`catalog_scenarios_execute`). The source gate also
  holds a proof to its scenarios: the API's member name (a type, trait or
  variant needs its own name, one of its methods, variants or trait items, or
  for a variant `Enum::Variant`) must be an identifier in a named scenario's
  body or in a fn, const or `impl` it reaches in the Showcase crate by call,
  `use` line or path (`crates/termrock-catalog/src/scenario_reach.rs`). A method or const
  whose name another exported type also uses (`new`, `len`, `key`, `render`)
  needs its owner type named in the scenario too, for example in a type
  annotation on the value it returns, because any other type's call would
  satisfy the bare name. Strings and comments
  do not count, and the check is still identifier matching, not behavioral
  proof. The one explicit exception is `VARIANT_SETS` in
  `crates/termrock-catalog/src/catalog_contract.rs` (`Metric::ALL` stands for the variants it lists).
  A proof whose scenario never calls its API fails the gate: add the call to
  the scenario with an assertion, re-point the proof, or make it a `Nonvisual`
  exception with a real regression test. Layer 3 is the
  tuiscotti journeys in `crates/termrock-functional/tests/functional`. Name matching is never behavioral
  proof. Run `cargo nextest run -p termrock-catalog -p termrock-showcase
  --all-features --no-tests fail -E 'test(catalog_)'` (the source gate is in
  `termrock-catalog`, the scenarios in `termrock-showcase`); the Rust crate CI jobs
  already run it. The proofs
  are split into lanes so parallel work never edits one file: a lane owns
  `apps/showcase/src/coverage/lane_<lane>.rs` (its proofs and exceptions),
  `apps/showcase/src/app_tests_catalog/<lane>.rs` (its cases and scenario
  functions) and its marked block of `ScenarioId`. The gate rejects a lane
  file that is not wired in. After a change
  moves many captures, `scripts/accept-changed-baselines.py` re-accepts each
  changed one through `scripts/accept-baseline.py` with `--expect-baseline` set
  to the digest in the tree (main's, after a rebase); `--dry` lists candidates.
  The inventory walks every crate of `docs/layering.toml` that exists
  (`crates/termrock-*`, #443) and spells each id the way the facade exports it,
  so a definition keeps its id when it moves into a crate behind a `pub use`;
  when it has several public spellings the one that already has a catalog line
  wins. `crates/termrock-catalog/tests/regressions/api-ids.sha256` holds the digest of the sorted ids of
  each matrix row (`catalog_api_ids_match_the_committed_digest`). A PR that moves
  code must not change it; a PR that adds or removes API on purpose reruns that
  test with `UPDATE_API_IDS=1` and commits the file. After a file with a
  `regression_test` moves, `python3 scripts/rewrite-regression-paths.py --dry`
  lists the stale paths in the coverage tables and without `--dry` rewrites them
  from `git diff -M`.

### Visual states

- Exactly one keyboard-focus indicator is visible at a time (the phosphor
  `▎` gutter from `Theme::gutter_symbol`/`Theme::gutter`), and it lives in
  the topmost layer. Content under a modal or popup shows no focus.
- A list whose focus belongs to an owner (a popup list under a search
  field, an editor or a select field) marks its cursor row with a fill
  (`Theme::cursor_row`, `CursorStyle::Fill`), never a second focus bar.
- The selected item of a tab strip or segmented control shows the
  phosphor accent while its page is the active layer (as macOS selection
  does in the active window), and goes neutral under a modal or popup.
  Keyboard focus is still only the single `▎` indicator, never the
  selection colour. Other chosen values (the current page in a list, a
  chosen option) follow `Theme::chosen_in`.
- The selected item of a list, tree, table, sidebar or menu keeps its
  accent fill, and a checked box, the on radio or toggle keeps its accent
  mark, when focus moves elsewhere in the same layer (owner decision
  2026-10-17, `InactiveSelection::Accent`, overriding macOS's neutral
  inactive selection, which stays available as `Neutral`). Both go
  neutral only under a modal or popup. Keyboard focus is still shown only
  by the single `▎`.
- A focused tab strip or segmented control shows the `▎` gutter like any
  focusable element; the selected item's accent is selection, not focus.
- A scrollbar thumb keeps one glyph in every state: rest is a neutral
  grey, hover a lighter grey, pressed (held or dragged) the accent. Where
  colour cannot carry state (`NO_COLOR`), a modifier does.
- A resize seam (`Splitter`, pane tree, master-detail, table column
  seams) is a thin rule (`│`/`─`) in the divider grey at rest, the heavy
  rule (`┃`/`━`) in a brighter grey on hover and the heavy rule in the
  phosphor accent while dragged (`Theme::ladders.seam`). Hover and drag
  restyle only the seam's own line of cells: no underline, no padding
  cells, no other seam or rule. In `NO_COLOR` the thumb modifiers carry
  hover and drag.
- Rest, hover and pressed are visibly different from each other, and from
  focused, selected and disabled, for every interactive element and at
  every colour level (truecolor, 256, 16, mono). Disabled controls do not
  react to hover or press.
- Text stays readable in every state: never the same colour as its
  background, and at least 4.5:1 contrast for text.

### Way of working

- Always use subagents for the work: parallel audits by category, and
  implementation agents in isolated worktrees on disjoint files. The main
  session coordinates, reviews and integrates.
- Never run more than 5 subagents in parallel. This is a hard ceiling at
  every moment, and it counts helpers that subagents start. Before
  starting one, the coordinator counts those still running; extra work
  waits in a queue. A subagent that starts a helper uses one of the 5.
- Each subagent commits and pushes its work in small portions as soon as
  each coherent step passes the gate, so no work is lost if it is stopped.
- Subagents never sit idle waiting: long commands run in the background
  while the agent keeps working, and an agent with nothing left but
  waiting ends its run and reports where to resume, rather than polling.
- No single command runs longer than 4 minutes: set an explicit timeout
  and split long jobs (nextest partitions, visual groups) into parts that
  fit.
- No command runs longer than 5 minutes without the agent acting on it:
  split long jobs into parts under 4 minutes, so the prompt cache stays
  warm.
- Deliver in small portions: commit and push to the working branch after
  every coherent step (one finding or one small group of related changes),
  as soon as the full gate passes. Never keep work uncommitted or unpushed
  for long; local-only state is a risk, not a convenience.
- Before each push: `git fetch` and rebase onto the remote branch, re-run
  the gate, then push. Never force-push shared branches.
- Concurrent agents serialize pushes with one lock: `mkdir
  "$(git rev-parse --git-common-dir)/push.lock"` and write an `owner` file
  inside it (branch and date), then fetch, rebase, gate on the exact HEAD,
  push, and always `rm -rf` the lock directory afterwards, on failure too.
  If `mkdir` fails, the lock is held: keep working and retry at the next
  checkpoint. Remove someone else's lock only when its owner file is older
  than 50 minutes.
- Handoff: whoever stops with unfinished work (coordinator or agent)
  pushes it to `wip/<name>` on origin and lists it (tip, item, state,
  exact next steps) in `docs/handoff/README.md` before stopping. On
  restart, read that file first and land or resume the `wip/*` branches
  before new work (`docs/GOAL.md`, "Continue from a handoff").
- Never `pkill -f`, `killall` or kill processes by name: other sessions and
  agents share the machine. Stop only processes (PIDs) and tasks you
  started yourself.
- Upstream PRs (velnor-new, tuiscotti): when the owner sends a link or
  says "check velnor-new" / "check tuiscotti" / "check upstream", follow
  the Upstream PR loop in `docs/upstream/README.md` and answer with one
  relay line per PR.
- Every finding raised in a review or audit is either fixed (by a subagent)
  or recorded with a reason in docs/audits; none is silently dropped.

### Proof

- Every behaviour fix ships with a regression test driven through the real
  app or widget (hit regions, focus and rendered cells), and that test must
  fail on the code before the fix.
- Run the full `cargo nextest run --workspace --all-targets --all-features`
  (the `jackin-console` tests are gated on the `demo` feature and are empty
  targets without `--all-features`), `cargo clippy --all-targets` and
  `cargo fmt --check` before reporting work as done. The
  visual baseline test must stay green unless a visual change is intended
  and stated.
