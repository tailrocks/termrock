## Live terminal (Ghostty-class)

This preview mounts one persistent Rust state machine. Focus it, use the current actions shown by the runtime, inspect the typed outcome, and use **Reset** for fresh state.

## Try it

- `Tab switch thumb`: Move through the real focus/selection model; the next action uses the new target.
- `←→ adjust`: Dispatch this action to the mounted Rust state machine and inspect its visible typed result.
- `Home/End`: Move through the real focus/selection model; the next action uses the new target.
- `drag either thumb`: Press, drag, and release on the visible handle; geometry/value follows the pointer.

Every accepted action reaches the same mounted Rust value. The status line shows the latest typed outcome; **Reset** creates a fresh instance.

## State and typed outcomes

`RangeSliderState` owns active thumb, range, drag, hover, and focus. The host consumes `ValueChanged`/`ThumbChanged` and decides how the range filters domain data.

## Usage

The Code view above and this source excerpt use the exact paint setup registered for `range-slider/basic`. Interaction state is long-lived in the catalog interactor; the host only forwards backend-neutral events.

```rust
use ratatui::prelude::*;
use termrock::{input::*, interaction::*, runtime::*, style::*, widgets::*};

// Exact paint setup used by the shared catalog story.
fn range_slider_basic_story(frame: &mut Frame<'_>, area: Rect, system: &DesignSystem) {
    let mut state = RangeSliderState::new(20.0, 80.0);
    state.set_focused(true);
    let _ = RangeSlider::new(SliderBounds::percent(), system)
        .label("Price filter")
        .paint(area, frame.buffer_mut(), &mut state);
}
```

## Common mistakes

- Do not treat separate Lookbook stories as runtime states or a slide sequence.
- Do not duplicate hit testing, focus, or keyboard rules in the host.
- Do not infer an action from visual styling; handle the widget's typed outcome.
