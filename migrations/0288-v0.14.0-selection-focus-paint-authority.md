# 0288 — One paint authority for selection, focus, and elevation

The token layer already knew how to paint a selected row, a focused container,
and an overlay. Widgets could bypass it, and the recipes themselves encoded a
few things that were not true: selection defaulted to a full neon fill, ten
collections forced their own chrome onto a cloned `DesignSystem`, every panel
filled from the same surface no matter how high it floated, and the backdrop
"dim" painted a stipple over an unchanged terminal background.

This migration makes the recipes the single authority and gives them honest
values.

## Selection is a gutter by default

`SelectionChrome::Gutter` is now `#[default]`; `Fill` is opt-in only.

| Preset | Before | After |
|--------|--------|-------|
| `DesignSystem::new(..)` / `SelectionChrome::default()` | `Fill` | `Gutter` |
| `DesignSystem::phosphor()` | `Tint` | `Gutter` |
| `DesignSystem::paper()` | `Fill` | `Tint` |
| `DesignSystem::high_contrast()` | `Fill` | `Tint` |

```rust
// Before — a saturated row fill, whatever the theme asked for
let system = DesignSystem::phosphor();
// After — same call, quiet row: ▌ gutter + strong label
// Opt back in explicitly where a fill is the point:
let system = DesignSystem::phosphor().selection(SelectionChrome::Fill);
```

The ten collections that used to clone the system and force
`SelectionChrome::Tint` (`select`, `quick_open`, `menu_bar`, `dropdown_menu`,
`command_palette`, `file_picker`, `history_picker`, `multi_select`,
`data_table`, `tree_table`) now resolve against the borrowed system, so a
consumer theme finally decides. `data_table`/`tree_table` also stop cloning a
whole `DesignSystem` per painted row.

A new integration gate, `crates/termrock/tests/design_gate.rs`, fails the build
if a widget reintroduces a local override. Its second gate — no widget paints
`Role::Selection` by default — ships `#[ignore]`d and is switched on by plan 009.

## `ListRowRecipe` loses `show_focus_underline`

Underline is not a focus cue (`docs/design/termrock-design-language.md` §5,
binding). The field is removed from the struct and from `resolve_list_row`.

```rust
// Before
if recipe.show_focus_underline {
    style = style.add_modifier(Modifier::UNDERLINED);
}
// After — the gutter and the strong label already say "selected here"
```

Two more `ListRowRecipe` changes:

- `hover` resolves from `Role::TextStrong` instead of `Role::LinkHover`; a
  hovered row lifts with `hover_wash` behind a strong label rather than
  borrowing hyperlink color.
- The gutter tracks collection focus: `Role::Accent` while the collection owns
  the keyboard, `Role::TextMuted` while it is parked. Selected-but-unfocused no
  longer looks identical to selected-and-focused.

## The surface ladder has five distinct rungs

`SurfaceRecipe` gains `Sunken`, `OverlayFocused`, and `OverlayDanger`, and
`Raised` stops sharing a role with `Overlay`:

| Recipe | Fill before | Fill after |
|--------|-------------|------------|
| `Raised` | `Role::Elevated` | `Role::Raised` |
| `Overlay` | `Role::Elevated` | `Role::Elevated` (unchanged) |
| `OverlayFocused` (new) | — | `Role::Elevated` + `Role::BorderFocused` |
| `OverlayDanger` (new) | — | `Role::Elevated` + `Role::Danger` |
| `Sunken` (new) | — | `Role::Sunken`, no border |
| `Selected` | `Role::Selection` | `Role::SelectionTint` |

`Elevation::Raised` maps to `Role::Raised` for the same reason
(`Elevation::Overlay` keeps `Role::Elevated`).

`Panel` gains `.overlay(bool)`. Overlay panels fill from the elevated rung and
pick the matching focused/danger recipe, so a dialog stops repainting the exact
surface it covers. The seven `Panel`-based overlays in this crate
(`permission`, `file_picker`, `history_picker`, `multi_select`, `form_wizard`,
`question_flow`, `date_time_picker`) set it.

```rust
// Before — an overlay indistinguishable from the panel behind it
let panel = Panel::new(system).emphasis(PanelChrome::Focused);
// After
let panel = Panel::new(system).overlay(true).emphasis(PanelChrome::Focused);
```

## `panel_recipe` takes an elevation, and danger marks its title

```rust
// Before
let recipe = system.panel_recipe(PanelChrome::Focused);
// After
let recipe = system.panel_recipe(PanelChrome::Focused, Elevation::Surface);
```

`PanelRecipe` gains `title_prefix: Option<&'static str>` — `Some(warning glyph)`
for `PanelChrome::Danger`, `None` otherwise — and `Panel` prepends it to the
title so danger chrome survives a colorless terminal instead of relying on a
red border.

## The backdrop actually dims

`Backdrop::from_tokens` paints `Role::BackdropWash` (a solid recede) instead of
a `░` field over `Color::Reset`. On a themed terminal the old backdrop changed
no background at all — it only sprinkled gray glyphs. `Backdrop::reset()` stays
for hosts that opt out; `Backdrop::dim_wash()` remains the stipple fallback and
no longer forces a background.

`render_backdrop` now takes the design system:

```rust
// Before
termrock::interaction::render_backdrop(frame, full_area);
// After
termrock::interaction::render_backdrop(frame, full_area, &system);
```

The dim stays host-driven on purpose: a widget's `render` only ever receives
its own rect, so painting the layer from inside a dialog could only ever cover
the dialog. Hosts call `render_backdrop` with the layer rect whenever
`stack.backdrop_policy()` is `Dim`.

`DialogVariant::Info` no longer forces `PanelChrome::Focused`: an unfocused
informational dialog stops wearing the focus border. Variant says what the
dialog is about; emphasis says whether it owns interaction.

## Button and input recipes stop lying

- Destructive buttons no longer set `fill = Role::Danger` (a foreground role —
  there was never a background there). They read through a danger label and a
  danger border, and `ControlState::Pressed` adds `REVERSED` so the press is
  the moment the button goes solid.
- `ControlState::Loading` is no longer folded into `Disabled`: the label keeps
  its variant identity and dims, so a loading action still looks like itself.
- `input_recipe` fills from `Role::Sunken` and takes its value color from
  `Role::Text` (patched with `Role::InputInvalid` when invalid) instead of
  reading both from `Role::Input`.
- Hovering an input washes the well with `Role::HoverTint` instead of
  brightening the border to `Role::Focus` — only focus moves the border.
- `InputRecipe.border` is documented as a border style; it never meant an
  underline.
