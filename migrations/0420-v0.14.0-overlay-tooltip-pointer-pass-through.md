# 0420: Overlay pointer routing honors input ownership

## Boundary

`OverlayStack::route_pointer` separates overlay geometry from pointer-input
ownership. A visible, non-input-owning overlay must not intercept a pointer
event destined for an input-owning layer below it.

## Change

`route_pointer` now evaluates each entry's `OverlayPolicy::owns_input` while
walking the stack from top to bottom:

- A hit on the top input-owning overlay returns `PointerRoute::Top`.
- A non-input-owning tooltip does not claim a hit. A hit on the next lower
  input-owning overlay returns `PointerRoute::Lower` for that layer.
- When no input-owning overlay is hit, including a stack containing only a
  tooltip, routing returns `PointerRoute::OutsideTop` instead of `Top`.

The builtin `OverlayKind::Tooltip` policy remains non-input-owning. Callers
that need a custom overlay to receive pointer input must set
`OverlayPolicy::owns_input` to `true`.

## Compatibility impact

Pointer routes can change from `Top` to `Lower` or `OutsideTop` when the
topmost geometry belongs to a tooltip or another non-input-owning overlay.
`OutsideTop` means that no input-owning overlay contains the position; it can
therefore be returned for a position inside a non-input-owning tooltip's
rectangle. Hosts must use the ownership-aware `PointerRoute` result, treat
`Lower` as the selected lower input-owning target, and must not dispatch
pointer input to a non-input-owning tooltip. `handle_outside_click` remains a
separate geometric outside-policy check against the top rectangle; it is not a
substitute for `route_pointer`'s ownership-aware result. No compatibility
alias preserves the old geometry-only routing behavior.
