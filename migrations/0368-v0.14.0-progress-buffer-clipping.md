# 0368 — v0.14.0 ProgressBar painting clips to its buffer

## Boundary

`ProgressBar::paint_state` and `ProgressBar::paint` accept a caller-provided
rectangle and write into a Ratatui buffer. Both entry points now intersect
that rectangle with the buffer area before state projection, recipe layout, or
cell writes. An empty or disjoint intersection is a no-op.

## Root cause

The public paint methods passed raw geometry into layout and text-writing
helpers. A rectangle outside an offset buffer could reach a direct cell write
or make a state paint acknowledge content that was never visible. Adding
checks inside individual glyph loops would leave other recipes exposed; the
buffer boundary belongs at both public paint entry points.

## Change

- Clip state-backed and builder-backed painting to `*buffer.area()`.
- Return before state projection or acknowledgement when the intersection is
  empty.
- Keep compact, detailed, multiline, determinate, and indeterminate rendering
  behavior unchanged inside the visible intersection.
- Keep the existing public signatures and widget delegates. `Widget::render`
  continues to call the same clipped `paint` method.

## Verification contract

Tests cover partial buffers with non-zero origins, left/top and right/bottom
clipping, fully outside and empty rectangles, multiline text, both progress
modes, widget rendering, and the rule that cells outside the intersection do
not change. A disjoint state paint must leave its dirty state pending.

## Host migration

Hosts should pass their normal layout rectangle. The reusable progress widget
owns buffer clipping; callers do not need to duplicate it.
