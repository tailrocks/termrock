# 0367 — v0.14.0 Overlay pointer routing honors input ownership

## Boundary

`OverlayStack::route_pointer` now uses each overlay's `owns_input` policy while
resolving a pointer target. Visible tooltip geometry remains paintable without
intercepting input meant for an input-owning overlay beneath it.

## Change

- The top input-owning hit returns `PointerRoute::Top`.
- A lower input-owning hit beneath a non-owning tooltip returns
  `PointerRoute::Lower` for that layer.
- When no input-owning overlay contains the point, routing returns
  `PointerRoute::OutsideTop`, including when the point is inside a tooltip's
  rectangle.
- Tooltip policy remains non-input-owning. Custom overlays that handle pointer
  input must set `OverlayPolicy::owns_input` to `true`.

## Compatibility impact

The enum shape is unchanged, but routing can now return `Lower` or
`OutsideTop` where geometry-only routing previously returned `Top` for a
non-input-owning top layer. Hosts should dispatch only to the input-owning
target named by the route. `handle_outside_click` remains a separate geometric
check against the top rectangle.

## Host migration

Use `route_pointer` to resolve the input target. Do not dispatch pointer input
to tooltip layers that only paint. No compatibility alias preserves the old
geometry-only routing behavior.
