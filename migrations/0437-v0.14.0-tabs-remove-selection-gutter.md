# 0437: Tabs restore canonical gutter, underline, and clipping geometry

## Boundary

Tabs no longer paint the `▎` selection gutter in a tab strip. The active rule
also spans the complete tab plane edge-to-edge, and `Tabs::paint` clips caller
geometry to the target buffer before any downstream painter writes. The
canonical Junie treatment reserves the bar for rows and fields; a tab
communicates its state through its plane, weight, marker, and underline instead.

## Evidence

The local `Tabs::paint_one_tab_in_rect` path currently writes
`DesignSystem::glyphs.selection_gutter()` at the left edge of every tab label
rectangle. Its focused-tab test consequently expects `▎` in the first cell.
The canonical `terminal-components-claude` Tabs widget intersects its paint
area with the buffer, paints the active rule from the tab's left edge through
its right edge, and its focused-tab test explicitly requires that a tab row
contain no `▎`. The canonical `DESIGN.md` Tabs section likewise says the bar
belongs to rows and fields, not tab strips, and requires an edge-to-edge active
underline.

## Root cause

Tabs reused the row/field focus-gutter painter instead of treating the tab
strip as its own state geometry. The call is unconditional: it computes a
state-aware gutter style, but never gates the glyph by a row or field context.
That makes a generic focus affordance appear in every tab item, including
unfocused and inactive tabs, and permits the visual contract to drift from the
canonical tab treatment. The active-rule loop also excluded both edge cells,
and the top-level paint path trusted caller rectangles even when they were
partially or wholly outside the buffer.

## Exact behavior

- `paint_one_tab_in_rect` stops writing `selection_gutter()`; rendered tab
  label rows contain no `▎`.
- The one-cell content inset remains. Labels, status glyphs, badges, close
  affordances, and the `TabsActiveCue::Marker` marker keep their existing
  positions relative to the tab rectangle.
- The active `TabsActiveCue::Rule` underline spans `rect.x..rect.right()`;
  the quiet-strip rule color remains border-strong and the inactive gap cells
  retain the canvas baseline.
- `Tabs::paint` intersects its requested area with `buffer.area()` before
  updating state or dispatching expanded, overflow, scrolling, or vertical
  painters. Partial and wholly out-of-bounds requests are safe no-ops outside
  the intersection.
- Overflow indicators, tab hit regions, close regions, keyboard handling, and
  semantic registration are unchanged.
- The change applies to expanded, overflow, scrolling, and vertical tab items
  that use the shared item painter. The already-collapsed select trigger was
  gutter-free and does not gain a second rendering path.
- No new opt-in or compatibility mode exists. A tab strip uses the canonical
  no-gutter treatment in every state.

## Validation

Update the focused Tabs rendering assertions to prove the full contract:

- expanded, inactive, overflow, and vertical label rows contain no `▎`;
- the one-cell content inset, edge-to-edge active underline, baseline, and
  tab/close hit regions remain present at their existing coordinates;
- partial and wholly out-of-bounds requested rectangles do not panic or write
  outside the buffer.

Run the focused widget tests and formatting check:

```sh
cargo test -p termrock tabs --all-features --locked --offline
cargo fmt --all -- --check
```

Also compare a two-row active/inactive strip with the canonical Tabs fixture;
the active tab keeps its plane and edge-to-edge rule, while no tab cell
contains the selection gutter glyph.

## Compatibility impact

This is a visual and paint-safety breaking change. Golden frames, screenshots,
and tests that expect `▎` at a tab's left edge or an inset active rule must be
updated. Consumers do not need source changes for the public `Tabs` API, state
transitions, event outcomes, tab geometry, or hit regions; the existing
one-cell inset intentionally keeps labels and controls from shifting.
Consumers must not add caller-side gutter padding or reintroduce the glyph.

No persisted data or serialized state changes. Rollback, if temporarily
required for an older visual baseline, is a source revision rollback rather
than a compatibility alias.
