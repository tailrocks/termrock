# 0444 — v0.14.0 MenuBar focused closed-bar gutter

## Boundary

The canonical `MenuBar` gives the keyboard cursor a one-cell `▎` focus gutter
when the bar owns focus and its cascade is closed. TermRock's full and compact
menu-bar paint path currently styles the active label but emits no focus
gutter and begins its label geometry at the left edge of the requested area.

This migration records the canonical focus-chrome and spacing contract for the
reusable `MenuBar`. The narrow `CommandPalette` replacement remains a separate
presentation and is not changed by this boundary. Open menu panels, menu-row
selection, mnemonics, and label hit semantics remain owned by their existing
paths.

## Canonical evidence

The reference implementation at
`/Users/donbeave/terminal-components-claude/src/widgets/menu.rs` implements
`MenuBar::render` as follows:

- it clips the render area to the buffer before painting;
- top-level labels use a padded `" {label} "` cell run;
- the first label starts at `area.x + 1`, leaving the leading cell available
  for the keyboard cursor gutter;
- the cursor label paints `▎` in the design-system focus color immediately
  before its label; and
- the cursor condition is `focused && cursor == i && open.is_none()`.

The reference `DESIGN.md` Menu bar section (the Menu bar and context-menu
anatomy around lines 954–965) explicitly requires that the keyboard cursor
shows the `▎` bar when the bar is focused and closed. The design token contract
also assigns the focus-gutter role to the primary accent color.

## Root cause

TermRock's `MenuBar::paint` full/compact branch uses `let mut x = area.x` and
writes each padded label directly. Its `active` calculation changes label
style, including the open-menu case, but there is no separate focus-chrome
step and no reserved leading cell. Focus therefore has no structural visual
owner, so the focused closed bar is indistinguishable from a merely styled
active label.

The enabling condition is the widget-level geometry/paint boundary: label
layout and focus indication are coupled only through text style. Fix the
reusable `MenuBar` geometry and paint contract; do not stamp a gutter from
application hosts or menu-panel callers.

## Closed and focused condition

For the full and compact menu-bar presentations:

- **Focused and closed:** when the bar owns keyboard focus and accepts input,
  its current top-level cursor label paints exactly one `▎` gutter. “Closed”
  means there is no open root/cascade menu (`open.is_none()` in the canonical
  state model).
- **Focused and open:** do not paint the closed-bar gutter. The open label
  joins the popover plane and the open cascade owns row selection styling.
- **Unfocused, input-gated, or hover-only:** do not paint the gutter. Hover
  may still lift a label, and mnemonic mode may still change label tone, but
  neither is a substitute for keyboard focus.
- **Cursor ownership:** only the current cursor label owns the gutter; sibling
  labels retain ordinary label styling and spacing.

## Exact geometry

Within the clipped one-row bar at `(area.x, area.y)`:

1. Preserve the existing bar background and optional brand placement. The
   first top-level label starts at `x = area.x + 1` (or at the equivalent
   post-brand position), not at the outer edge.
2. Render the label as the display-width run `" {label} "`. If its width is
   `w`, its hit rectangle remains `Rect::new(x, area.y, w, 1)`.
3. For the focused cursor label while closed, paint `▎` at
   `(x.saturating_sub(1), area.y)`, exactly one cell wide, with focus-color
   foreground and the bar background. This places the gutter in the reserved
   cell immediately before the label's leading space.
4. Advance to the next label with `x += w + 1`, preserving the canonical
   one-cell inter-label gap. The gutter must not overwrite label text, the
   brand, or a neighboring hit region.
5. Use display-cell width for Unicode labels and keep clipping/overflow safe;
   a partially visible label must not write outside the clipped buffer area.

The existing label text, compact presentation, click rectangles, open-menu
anchor, and semantic/control registration remain unchanged except for the
one-cell reserve required by this geometry.

## Validation

The implementation must add or update focused `MenuBar` tests proving:

- a focused, closed full bar paints exactly one `▎` at the cursor label's
  preceding cell and applies the focused label style;
- an unfocused or input-gated bar, a hover-only bar, and a focused open
  cascade paint no closed-bar gutter;
- the first label begins at the reserved `area.x + 1` cell, later labels keep
  their one-cell gaps, and hit rectangles still cover only label cells;
- moving the cursor moves the single gutter without leaving stale glyphs;
- brand placement, open-label popover styling, mnemonic mode, compact/narrow
  behavior, Unicode display widths, and clipped/tiny areas remain safe; and
- the `CommandPalette` narrow replacement remains unchanged.

Required gates for the source implementation:


Compare focused-closed, focused-open, unfocused, compact, narrow, branded,
and Unicode frames against the canonical MenuBar fixture. The comparison must
show one and only one closed-bar gutter, exact label/hit geometry, and no
gutter on the open cascade's command rows.

## Visual breaking impact

Focused closed menu bars gain a visible accent `▎` immediately before the
current top-level label. Reserving that cell shifts labels and their hit
rectangles right by one cell (and leaves one fewer cell for later labels), so
compact truncation, narrow overflow, screenshots, and goldens can change.

Unfocused bars, open cascades, and command-palette replacements do not gain
this closed-bar gutter. Hosts that relied on labels beginning at the outer
edge must update visual expectations; they must not compensate by painting a
second gutter or changing menu hit regions themselves.

## Compatibility policy

There is no compatibility shim, legacy-layout flag, alias geometry, dual
rendering path, or host-side gutter helper. The canonical focused-closed
geometry is the only `MenuBar` contract. Consumers must update visual
baselines and any hard-coded assumptions about the first label cell. A
temporary rollback, if required for an old fixture, is a source-revision
rollback.
